## What matters first

Markdown footnotes are useful, but they are not the safest portable syntax feature. Treat them as a renderer-dependent extension unless you control the output environment and know footnotes are supported.

## Standard example

```md
Here is a sentence with a footnote.[^1]

[^1]: This is the footnote text.
```

## Why footnotes feel deceptive

Footnotes look clean in well-supported renderers, so people assume they are universally safe. They are not.

The real issue is that footnotes sit in the zone where:

- some tools support them well,
- some tools ignore them,
- and some tools partially support them but produce awkward output in export.

That makes them different from headings, links, or plain lists.

## When footnotes are a good choice

Footnotes are reasonable when:

- the publishing environment is known,
- the audience benefits from reduced in-line clutter,
- the content is still primarily HTML or docs-page output,
- and you have tested the actual renderer.

They are especially defensible in long-form essays, technical notes, or editorial content where side comments would otherwise interrupt the flow.

## When footnotes are a poor choice

Footnotes are a poor choice when:

- the file must remain highly portable,
- the content will move through multiple unknown renderers,
- screenshots or image exports are important,
- or the note must remain easy to read in raw plain text.

In those cases, a short in-line note or a clearly labeled `Notes` section is often safer.

## The fallback pattern

If footnotes are not safe enough for the workflow, use:

- a short parenthetical note,
- an end-of-section note block,
- or a `Notes` subsection with normal links and references.

That is less elegant, but usually more stable.


## Notes-section fallback example

Instead of a footnote:

```md
The renderer changed its heading IDs after publishing.[^1]

[^1]: This is common when duplicate headings or punctuation-heavy headings are involved.
```

Use an explicit notes section:

```md
The renderer changed its heading IDs after publishing.

## Notes

- Duplicate headings and punctuation-heavy headings can change generated anchor IDs.
```

The notes section is less compact, but it survives more renderers, exports, and copy-paste workflows.

## Footnotes in exports

Footnotes become risky when Markdown is exported to:

- PDF generators that restyle or move notes;
- CMS fields that strip the footnote extension;
- email systems that flatten links and backreferences;
- image exports where the backreference behavior is meaningless;
- AI prompt contexts where note references may be separated from their definitions.

If the note is essential to understanding, keep it near the claim or use a normal section. Footnotes are best for supporting context, not critical instructions.

## Authoring rule for teams

Teams should document whether footnotes are allowed in each publishing path:

| Path | Footnote policy |
| --- | --- |
| GitHub README only | Usually acceptable if preview confirms rendering |
| Docs site with known MDX/Markdown support | Acceptable when the build supports the syntax |
| CMS reuse or multi-channel publishing | Prefer notes sections or inline notes |
| Markdown-to-image workflows | Avoid footnotes unless they render visibly in the final image |

That policy prevents one author from adding elegant footnotes that break downstream workflows.

## Recommended operating rule

Use footnotes only when the rendering path is known and the gain in readability is real. Otherwise, prefer normal prose and explicit note sections.
