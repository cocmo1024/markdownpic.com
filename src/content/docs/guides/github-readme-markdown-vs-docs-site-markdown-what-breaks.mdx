# GitHub README Markdown vs docs-site Markdown: what breaks

Many teams assume Markdown written for a README will move cleanly into a docs site. Sometimes it does. Often it does not. The reason is simple: a README renderer and a docs-site pipeline are solving different problems. GitHub optimizes for repository reading. Docs systems optimize for navigation, theming, metadata, and site structure.

## What matters first

README Markdown and docs-site Markdown overlap heavily, but they are not the same operating environment.

The common breakpoints are:

- frontmatter and page metadata;
- heading IDs and generated anchors;
- callouts, alerts, and custom components;
- relative paths for links and assets;
- raw HTML that depends on site styling;
- table-of-contents behavior;
- and any syntax that was only "safe enough" inside GitHub.

If the file must live in both places, author for the stricter path.

## The highest-friction differences

| Difference | Why it breaks reuse |
| --- | --- |
| Relative links | Repo-relative paths often do not match site routing |
| Image paths | README asset conventions may not survive docs build output |
| Frontmatter | Docs sites often need it; READMEs often ignore it |
| Alerts and components | GitHub alerts are not universal docs components |
| Raw HTML | Docs systems may sanitize differently or replace the need with components |
| Heading IDs | Generated anchors may not match GitHub behavior |

These are not edge cases. They are the normal reasons shared Markdown sources become messy.

## The safest shared-source model

If one source must serve both:

1. keep the body in portable Markdown;
2. isolate site-specific metadata from reusable content where possible;
3. minimize renderer-specific callouts or component syntax;
4. treat links and assets as a deliberate compatibility layer, not an afterthought.

## When separate sources are justified

Sometimes two sources are cleaner than one. That becomes justified when the README is a repository landing page with marketing-like behavior, the docs site needs structured navigation and components, or the team keeps compromising readability in both places to preserve one file.

Shared source is valuable, but only if it reduces complexity overall.

## Breakage checklist before reuse

Before moving README Markdown into a docs site, inspect these areas:

| Area | README behavior | Docs-site risk |
| --- | --- | --- |
| Heading hierarchy | Often optimized for repository scanning | May conflict with sidebar, page title, and generated TOC |
| Relative links | Usually repo-relative | May need root-relative or route-relative links |
| Images | Often point to repository assets | Build output may move or fingerprint assets |
| Badges | Common at the top of READMEs | Can look noisy or fail in print/PDF exports |
| HTML | GitHub may sanitize but still allow useful fragments | Docs sites may strip, transform, or style HTML differently |
| Alerts/callouts | GitHub-specific alert syntax may work in README | Other renderers may treat it as plain blockquote text |
| Frontmatter | Usually absent or ignored | Docs sites often require title, description, layout, or nav metadata |

This checklist prevents the common mistake of treating "renders on GitHub" as proof that the source is portable.

## Safer shared-source pattern

If the README and docs site must share source, keep the reusable body plain and move platform-specific behavior to wrapper layers:

```md
# Project or feature name

Short overview written in normal Markdown.

## Install

Use portable fenced code blocks and normal links.

## Usage

Keep examples independent of site-only components.
```

Then let the docs site add navigation, callouts, tabs, framework components, or generated metadata around that content. The Markdown file remains reusable because it does not depend on one renderer's custom features.

## When GitHub-specific Markdown is acceptable

GitHub-specific patterns are acceptable when the file is clearly a GitHub README and not intended to be canonical source for a docs site. Examples include:

- status badges for repository health;
- issue and pull-request references;
- GitHub alert syntax;
- repository-relative links;
- contributor instructions tied to GitHub workflows.

Those patterns are useful in a README. They become risky only when the same file is expected to behave like cross-platform documentation.

## Practical migration workflow

For a migration, use this order:

1. copy the README into the docs site as a draft page;
2. run the docs build and inspect broken links, assets, callouts, and headings;
3. replace GitHub-specific behavior with renderer-supported patterns;
4. decide which content belongs in the README versus the docs page;
5. add canonical links between the two so readers do not land in a dead end.

This keeps the docs site useful without stripping the README of the repository context that makes it valuable.
